\section{Método}

\subsection{Diseño metodológico y solución propuesta}

La metodología del presente trabajo se plantea desde una investigación aplicada de enfoque cuantitativo, orientada al pronóstico univariado de demanda eléctrica y a la construcción de una aplicación de escritorio que permita ejecutar dicho procedimiento de forma reproducible. Su carácter aplicado se debe a que el proyecto no se limita a estudiar el desempeño de un modelo de forma aislada, sino que integra el proceso de carga, validación, entrenamiento, almacenamiento y generación de pronósticos dentro de una solución tecnológica funcional.

El diseño es no experimental, ya que la demanda eléctrica se analiza a partir de registros históricos observados, sin manipular directamente las condiciones que originan el consumo. La variable de interés corresponde a la carga eléctrica registrada en el tiempo, por lo que cada observación conserva una dependencia directa con su posición cronológica. Esta condición hace necesario respetar el orden temporal durante la preparación de los datos, el entrenamiento del modelo y la evaluación posterior del pronóstico.

La solución propuesta consiste en una aplicación de escritorio para trabajar con series temporales de demanda eléctrica bajo un contrato de datos uniforme. En este flujo, la serie se representa mediante una columna temporal y una columna de valores observados, identificadas en la aplicación como \texttt{timestamp} y \texttt{y}. Esta estructura permite que los datos preparados a partir de Open Power System Data o importados desde archivos externos puedan procesarse bajo las mismas reglas de validación y modelado.

Desde una perspectiva general, el sistema organiza el proceso completo desde la disponibilidad de una serie histórica hasta la obtención de un pronóstico. Primero, la aplicación permite seleccionar o importar una serie válida; después, verifica su estructura básica, su continuidad temporal y la consistencia de los valores observados. Posteriormente, el usuario puede definir el tramo de datos que será empleado para el entrenamiento y configurar los parámetros principales del modelo N-BEATS, como la frecuencia temporal, el horizonte de predicción y la ventana histórica de entrada.

La solución también considera la persistencia de los artefactos generados durante el proceso. Cada entrenamiento produce un modelo guardado junto con su configuración, metadatos y el conjunto exacto de datos utilizado. De forma posterior, ese modelo puede cargarse para generar pronósticos a partir de un contexto histórico reciente. Con ello, la metodología articula dos dimensiones complementarias: la evaluación empírica del modelo de pronóstico y la implementación de una herramienta que permite operar el flujo de manera reproducible.

\subsection{Datos utilizados y preparación de la serie}

Los datos base del proyecto provienen del paquete \emph{Time series} de Open Power System Data, una fuente pública que recopila y estandariza series temporales del sector eléctrico europeo. En particular, se utiliza el archivo \texttt{time\_series\_60min\_singleindex.csv}, que contiene registros horarios asociados con demanda, generación, precios y otras variables del sistema eléctrico. Para el alcance de este trabajo se consideran únicamente las columnas de demanda eléctrica real, identificadas por el sufijo \texttt{\_load\_actual\_entsoe\_transparency}. Por tanto, se excluyen variables de pronóstico, precios, generación solar, generación eólica, intercambios y cualquier otra columna que no represente carga real observada.

La columna temporal del archivo original corresponde a \texttt{utc\_timestamp}. Cada columna de demanda real se interpreta como una zona candidata, país o área del sistema eléctrico, y se transforma de manera independiente en una serie temporal univariada. Esta decisión mantiene la coherencia con el enfoque del proyecto, ya que el modelo se entrena únicamente con la trayectoria histórica de la variable objetivo y no incorpora variables exógenas como temperatura, humedad, calendario, generación renovable o indicadores económicos. En consecuencia, no se construye una serie multivariada ni se utiliza la demanda de una zona como variable explicativa de otra.

La preparación de cada serie consiste en transformar los datos al contrato operativo requerido por la aplicación. Para ello, \texttt{utc\_timestamp} se convierte en una columna denominada \texttt{timestamp}, mientras que la columna de demanda seleccionada se renombra como \texttt{y}. Este formato permite que distintas zonas de Open Power System Data puedan procesarse bajo las mismas reglas de validación, entrenamiento y pronóstico. El mismo contrato se aplica a los datos externos ingresados por el usuario: la aplicación puede trabajar con archivos propios siempre que incluyan una columna temporal \texttt{timestamp} y una columna numérica \texttt{y}.

Antes de utilizar una zona como entrada del modelo, se aplican validaciones orientadas a garantizar su consistencia temporal y numérica. En primer lugar, las marcas temporales se convierten a fechas interpretables y los valores de demanda se convierten a formato numérico. Posteriormente, las observaciones se ordenan cronológicamente, se revisan duplicados temporales, valores faltantes y discontinuidades en la frecuencia. Una zona se considera utilizable cuando dispone de un tramo continuo suficientemente amplio para cubrir la ventana histórica de entrada, el horizonte de predicción y el procedimiento de evaluación definido para el experimento.

Como apoyo reproducible para esta preparación, el proyecto contempla notebooks de exploración y procesamiento. El notebook \texttt{01\_exploration.ipynb} permite inspeccionar el archivo crudo, identificar columnas de demanda real, revisar cobertura temporal, nulos y duplicados. El notebook \texttt{02\_prepare\_country\_datasets.ipynb} transforma zonas seleccionadas al contrato \texttt{timestamp}/\texttt{y} y exporta archivos procesados. Además, \texttt{04\_build\_opsd\_zone\_catalog.ipynb} construye un catálogo de zonas disponibles a partir de la metadata de Open Power System Data. Estos notebooks no sustituyen el flujo de la aplicación, sino que documentan y respaldan la preparación de los datos utilizados.

Para las pruebas y la comparación de resultados se selecciona Austria (\texttt{AT}) como caso de estudio principal. Su columna original en Open Power System Data corresponde a \path{AT_load_actual_entsoe_transparency}. En el archivo procesado \texttt{AT.csv}, la serie contiene 50,400 observaciones horarias entre el 1 de enero de 2015 a las 00:00 UTC y el 30 de septiembre de 2020 a las 23:00 UTC. La revisión del archivo no identifica marcas temporales duplicadas, valores faltantes en \texttt{y} ni huecos en la frecuencia horaria, por lo que la serie queda lista para aplicar el protocolo de entrenamiento y evaluación. Aunque el flujo de preparación permite trabajar con otras zonas del paquete, el análisis experimental reportado en este documento se limita a \texttt{AT} para mantener una comparación controlada entre N-BEATS y ARIMA bajo una misma serie, los mismos horizontes y los mismos tramos temporales.

\subsection{Formulación del problema de pronóstico}

El problema abordado se trabaja como un pronóstico univariado multi-step de demanda eléctrica horaria. En términos operativos, la aplicación recibe una serie ordenada bajo el contrato \texttt{timestamp}/\texttt{y}, toma un bloque reciente de observaciones históricas y genera una secuencia de valores futuros para el horizonte configurado. El modelo no recibe variables exógenas como temperatura, calendario, precios, generación o indicadores económicos; toda la información disponible para el pronóstico proviene de la trayectoria pasada de la demanda.

En la aplicación, la longitud del contexto histórico se controla mediante el parámetro \texttt{input\_size}. Antes de generar una predicción, el sistema verifica que la serie de contexto contenga al menos esa cantidad de observaciones y utiliza las últimas filas disponibles como entrada del modelo. El horizonte de salida se controla mediante el parámetro \texttt{horizon}, que determina cuántas horas futuras se estiman en una sola ejecución. La salida generada se almacena bajo la columna \texttt{yhat}, mientras que los valores observados usados para evaluación conservan el nombre \texttt{y}. Esta convención permite comparar el pronóstico contra la serie real mediante métricas de error calculadas sobre los mismos timestamps.

Los experimentos consideran cuatro horizontes de predicción: 24, 168, 336 y 720 horas. Estos horizontes representan escenarios de corto plazo diario, semanal, bisemanal y mensual, respectivamente. Para cada horizonte se define una ventana histórica proporcional al alcance del pronóstico: 168 observaciones para 24 horas, 672 para 168 horas, 1344 para 336 horas y 2160 para 720 horas. Esta configuración permite que N-BEATS reciba suficiente contexto temporal para capturar patrones horarios y semanales relevantes antes de generar la predicción.

La comparación con ARIMA se formula bajo la misma variable objetivo y los mismos timestamps de evaluación. Sin embargo, ARIMA no utiliza una ventana de entrada fija equivalente a \texttt{input\_size}; en su lugar, el modelo se ajusta sobre una ventana histórica de entrenamiento previa al origen de pronóstico. Para mantener la viabilidad computacional del baseline estadístico, se emplean como máximo los últimos dos años de observaciones horarias antes de cada horizonte evaluado. De esta manera, ambos modelos se comparan sobre el mismo tramo futuro, aunque su forma de utilizar la historia sea distinta por la naturaleza de cada método.

\subsection{Configuración del modelo y referencia comparativa}

El modelo principal del proyecto corresponde a N-BEATS, implementado dentro de la aplicación de escritorio como el componente encargado de transformar una ventana histórica de demanda eléctrica en un horizonte futuro de pronóstico. La configuración experimental se define de acuerdo con la frecuencia horaria de la serie y con los horizontes de evaluación seleccionados. En todos los casos, la frecuencia temporal se establece como horaria (\texttt{freq = h}) y la variable objetivo corresponde exclusivamente a la columna \texttt{y}.

Para cada horizonte se entrena un modelo N-BEATS independiente. Esta decisión permite ajustar la longitud de entrada y el número de pasos de entrenamiento al alcance temporal de cada experimento, evitando usar una única configuración para horizontes de dificultad distinta. La ventana de entrada se elige de forma proporcional al horizonte. Para el escenario diario, el modelo recibe una semana de observaciones horarias previas; para el semanal, cuatro semanas; para el bisemanal, ocho semanas; y para el mensual, noventa días de contexto. Esta relación busca proporcionar al modelo suficiente historia reciente para capturar patrones de corto plazo, especialmente la estacionalidad diaria y semanal presente en la demanda eléctrica horaria. El parámetro \texttt{max\_steps} controla la duración máxima del entrenamiento y se incrementa en los horizontes más largos debido a la mayor complejidad de la salida esperada.

Como referencia comparativa se emplea un modelo ARIMA automático. Su función dentro del estudio no es sustituir al modelo principal ni formar parte del flujo funcional de la aplicación, sino servir como baseline estadístico externo para evaluar si N-BEATS ofrece un desempeño competitivo frente a una familia tradicional de modelos de series temporales. Para ello se utiliza \texttt{AutoARIMA} de la librería \texttt{statsforecast}, configurado con periodicidad estacional diaria mediante \texttt{season\_length = 24}. Esta configuración permite que el modelo considere patrones estacionales de 24 horas, coherentes con la frecuencia horaria de la serie de demanda.

El baseline ARIMA se ajusta de manera independiente para cada horizonte, utilizando como entrenamiento los datos disponibles antes del origen de pronóstico correspondiente. Para mantener la viabilidad computacional del ajuste estadístico, se limita el entrenamiento a los últimos dos años de observaciones horarias previas a cada tramo evaluado. A diferencia de N-BEATS, ARIMA no utiliza un parámetro equivalente a \texttt{input\_size}; su ajuste se basa en la estimación de una estructura autorregresiva, de diferenciación y de media móvil sobre una ventana histórica de entrenamiento.

La comparación entre N-BEATS y ARIMA se diseña bajo una condición común: ambos modelos se evalúan sobre la misma serie, los mismos horizontes y exactamente los mismos timestamps de prueba. De esta manera, las diferencias observadas en MAE, RMSE y MAPE pueden atribuirse al comportamiento de los modelos bajo el protocolo definido, y no a diferencias en los periodos evaluados o en la variable objetivo.

\subsection{Implementación de la aplicación de escritorio}

La aplicación de escritorio se implementa como una herramienta local orientada a organizar el flujo completo de trabajo: disponibilidad de datos, selección de series, entrenamiento de modelos N-BEATS, almacenamiento de artefactos y generación posterior de pronósticos. La interfaz se construye con Flet, lo que permite desarrollar una aplicación gráfica en Python y mantener la lógica del sistema integrada con los módulos de preparación, entrenamiento y pronóstico. Al iniciar, la aplicación prepara un espacio de trabajo local en el directorio \path{~/Energy Forecast app}, donde se almacenan datos, configuraciones, modelos entrenados y ejecuciones de forecast.

El espacio de trabajo se estructura en carpetas separadas para mantener trazabilidad entre datos y artefactos sin mezclar archivos de ejecución con el código fuente del proyecto. Su organización principal es la siguiente:

\begin{codeblock}{Estructura del workspace externo}
    ~/Energy Forecast app/
    |-- settings.json
    |-- data/
    |   |-- raw/
    |   |-- processed/
    |   |-- imported/
    |   `-- reference/
    `-- models/
    `-- mdl_*/
    |-- config.json
    |-- metadata.json
    |-- neuralforecast/
    `-- runs/
    `-- run_*/
    |-- forecast_input.csv
    |-- forecast.csv
    `-- metadata.json
\end{codeblock}

En esta estructura, \path{data/raw} conserva los archivos crudos de Open Power System Data, \path{data/processed} contiene series normalizadas bajo el contrato \texttt{timestamp}/\texttt{y}, \path{data/imported} almacena archivos cargados por el usuario y \path{data/reference} guarda información auxiliar, como el catálogo de zonas disponibles. La carpeta \path{models} concentra los modelos entrenados y las ejecuciones de pronóstico asociadas a cada modelo.

Desde el punto de vista funcional, la aplicación se organiza alrededor de cuatro vistas principales. La primera corresponde a la selección de modelos, donde se listan los modelos N-BEATS disponibles, se permite filtrarlos por dataset, horizonte, ventana de entrada, frecuencia o número de pasos de entrenamiento, y se ofrece acceso a la creación de nuevos modelos. La segunda vista corresponde a la creación de modelos, donde el usuario selecciona un dataset procesado o importado, inspecciona una vista previa de la serie, define el tramo de entrenamiento y configura parámetros como \texttt{freq}, \texttt{horizon}, \texttt{input\_size} y \texttt{max\_steps}. La tercera vista corresponde al espacio de pronóstico de un modelo, donde se selecciona una fuente de contexto histórico y se genera un nuevo forecast. Finalmente, la vista de historial permite consultar ejecuciones previas y revisar los archivos generados por cada pronóstico.

El proceso de entrenamiento se ejecuta mediante un servicio especializado que recibe la serie seleccionada, valida su estructura y ajusta un modelo N-BEATS con la configuración indicada. La selección del conjunto de entrenamiento puede realizarse sobre todo el dataset, las primeras \(N\) filas, un rango de filas o un rango de fechas. Antes del ajuste, el sistema verifica que el tramo seleccionado contenga al menos \texttt{input\_size + horizon} observaciones, de modo que exista suficiente historia para construir ventanas de entrada y salidas de entrenamiento. Al finalizar, el modelo se guarda en una carpeta identificada con un \texttt{id} del tipo \texttt{mdl\_*}, junto con el modelo serializado por NeuralForecast, un archivo \texttt{config.json} y un archivo \texttt{metadata.json}.

La trazabilidad del entrenamiento se apoya en esos metadatos. El archivo \texttt{config.json} registra la frecuencia, el horizonte, la ventana de entrada, el número máximo de pasos y la configuración técnica del adaptador. El archivo \texttt{metadata.json} registra el dataset, el archivo fuente, el modo de selección, los parámetros de selección, el rango temporal usado, el número de filas y la configuración de cómputo. La aplicación no guarda una copia CSV inmutable del subconjunto de entrenamiento; en cambio, conserva las referencias necesarias para reconstruirlo a partir del archivo fuente original, siempre que dicho archivo se mantenga disponible y sin cambios.

La generación de pronósticos se realiza cargando un modelo N-BEATS previamente entrenado y proporcionando una serie de contexto con el mismo contrato \texttt{timestamp}/\texttt{y}. El sistema valida que el contexto contenga al menos \texttt{input\_size} observaciones y utiliza las últimas filas necesarias como entrada del modelo. El resultado se exporta como un archivo \texttt{forecast.csv}, compuesto por las columnas \texttt{timestamp} y \texttt{yhat}. Además, se guarda el archivo \texttt{forecast\_input.csv}, que contiene el contexto histórico usado para generar el pronóstico, y un archivo \texttt{metadata.json}, que registra el identificador del modelo, el identificador de la ejecución, el horizonte, la ventana de entrada, la fecha de generación y las rutas relativas de los artefactos.

La persistencia de artefactos constituye una parte central de la implementación. Cada modelo entrenado queda almacenado en \path{models/mdl_*}, mientras que cada ejecución de pronóstico se guarda en una subcarpeta \path{runs/run_*} dentro del modelo correspondiente. Esta convención permite distinguir entre el artefacto del modelo y las distintas predicciones generadas a partir de él. Cada run conserva el contexto histórico usado por el modelo en \texttt{forecast\_input.csv}, el pronóstico generado en \texttt{forecast.csv} y sus metadatos en \texttt{metadata.json}.

El diseño separa la interfaz de usuario de los servicios internos. Las vistas de escritorio se encargan de recibir parámetros, mostrar estados y presentar resultados, mientras que los servicios de entrenamiento y pronóstico concentran la lógica de validación, ajuste del modelo, generación de predicciones y escritura de archivos. Esta separación mejora la mantenibilidad del sistema y permite que los mismos flujos puedan verificarse desde notebooks o scripts sin depender exclusivamente de la interfaz gráfica.

En conjunto, la aplicación implementa un flujo reproducible para trabajar con demanda eléctrica univariada: prepara un workspace local, permite seleccionar o importar series bajo un contrato común, entrena modelos N-BEATS configurables, conserva sus artefactos y genera pronósticos reutilizables. De esta forma, el producto desarrollado no solo sirve como soporte para los experimentos del documento, sino también como una herramienta funcional para ejecutar el proceso de pronóstico sobre series horarias compatibles.

\subsection{Estrategia de evaluación}

La evaluación del desempeño se organiza en dos niveles complementarios. El primero corresponde a la estimación de errores de pronóstico mediante métricas cuantitativas calculadas sobre los mismos tramos temporales para ambos modelos. El segundo corresponde a la verificación funcional de la aplicación de escritorio, que asegura que el flujo completo opera de manera reproducible.

\subsubsection{Evaluación cuantitativa de los modelos}

La comparación entre N-BEATS y ARIMA se realiza exclusivamente sobre la serie de Austria (\texttt{AT}) en cuatro escenarios definidos por el horizonte de predicción: 24, 168, 336 y 720 horas. Para cada escenario, ambos modelos se evalúan sobre exactamente los mismos timestamps. N-BEATS fue entrenado con el bloque de datos entre el 1 de enero de 2015 y el 31 de diciembre de 2018. A partir de ese entrenamiento, cada horizonte utiliza un origen de pronóstico distinto, determinado por la ventana de entrada que consume el modelo: 168 horas previas para el horizonte diario, 672 para el semanal, 1344 para el bisemanal y 2160 para el mensual, lo que sitúa los inicios de pronóstico el 8 de enero, el 29 de enero, el 26 de febrero y el 1 de abril de 2019, respectivamente. Esta configuración refleja el modo de operación real del modelo en la aplicación: el usuario proporciona un contexto histórico reciente y obtiene un pronóstico hacia adelante.

ARIMA, en cambio, se ajusta de manera independiente para cada horizonte utilizando los últimos dos años de observaciones horarias previas al origen de pronóstico correspondiente. Esta decisión responde a la necesidad de mantener viable el ajuste estadístico sobre series largas y refleja una práctica documentada en la aplicación de modelos ARIMA a datos de alta frecuencia horaria, donde entrenar con una ventana histórica excesivamente extensa puede introducir ruido estructural sin mejorar necesariamente la calidad del pronóstico.

Las métricas de error utilizadas son el error absoluto medio (MAE), la raíz del error cuadrático medio (RMSE) y el error porcentual absoluto medio (MAPE). El MAE expresa la magnitud promedio del error en las mismas unidades de la demanda eléctrica; el RMSE penaliza con mayor intensidad los errores grandes, lo que resulta pertinente en un contexto donde los picos de demanda tienen mayor impacto operativo; y el MAPE facilita una lectura relativa del desempeño. La combinación de las tres métricas evita reducir la evaluación a una sola cifra y permite identificar si un modelo es consistentemente mejor o si su ventaja depende del horizonte o de la métrica considerada.

El cálculo de errores se implementa mediante notebooks independientes que permiten verificar y reproducir los resultados. El notebook \texttt{05\_arima\_baseline.ipynb} genera los forecasts ARIMA y los exporta como archivos con columnas \texttt{timestamp}, \texttt{y} e \texttt{yhat}. Los notebooks \texttt{06\_arima\_error\_metrics.ipynb} y \texttt{07\_nbeats\_error\_metrics.ipynb} recalculan MAE, RMSE y MAPE para cada modelo por separado a partir de los forecasts disponibles, de modo que las métricas puedan obtenerse incluso si uno de los modelos no ha finalizado su ejecución. El notebook \texttt{08\_model\_error\_comparison.ipynb} consolida ambas fuentes, valida que los timestamps de evaluación coincidan exactamente y produce las tablas comparativas finales.

\subsubsection{Evaluación funcional de la aplicación}

Además de las métricas de pronóstico, se verifica que la aplicación de escritorio complete correctamente el flujo operativo para el cual fue diseñada. Esta verificación incluye: la preparación automática del espacio de trabajo en \path{~/Energy Forecast app}, la descarga y procesamiento de datos desde Open Power System Data, la validación de la estructura \texttt{timestamp}/\texttt{y}, la creación de modelos N-BEATS con configuraciones específicas, la persistencia del modelo entrenado junto con su configuración y metadatos, y la generación de pronósticos con almacenamiento de ejecuciones en \path{runs/run\_*}. La evaluación funcional no asigna una calificación numérica, sino que documenta la completitud del flujo implementado y la trazabilidad de los artefactos producidos, lo cual constituye un criterio de calidad para una herramienta orientada a la reproducibilidad.
